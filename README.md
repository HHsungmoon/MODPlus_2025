# MODPlus_2025

## 1. 프로젝트 배경 및 목표

### ✅ 프로젝트 개요

진행 인원 : 한양대학교 컴퓨터소프트웨어학부 홍성문.

진행 기간 : 2025년 2월 24일 ~ 10월 31일.

진행 상황 : 멀티스레드 리팩토링및 알고리즘/자료구조 개선 완료. 

Details : https://www.notion.so/MODPlus-1f1038bdc42b803aa2c7c1b25b63cc33?source=copy_link

최종 성능 : 36코어 서버에서 36배 이상 빠른 성능 달성.
- CPU 코어 갯수 만큼 분석 시간이 일정하게 단축된다.
- 분석 속도 개선을 통해 **연구시간 단축 및 효율적 실험 진행**이 가능해 **생명공학 연구에 실질적 기여**가 예상됩니다.

### ✅ 프로젝트의 설명

본 프로젝트는 단백질의 **PTM** 분석을 효과적으로 수행할 수 있는 도구인 **MODplus**의 성능을 개선하기 위한 프로젝트입니다. Java로 구현된 기존 싱글 스레드 기반 코드를 **멀티스레드** 구조로 전환해 성능을 최대한 향상시키는 방식으로 리팩토링을 진행합니다. 또한 MODplus 실행 결과의 **정확도 일관성**과 **스레드 간 동시성**을 보장하며, 최신 JDK 및 라이브러리를 활용한 **모듈화**,  `Dynamic Programming` 기반 알고리즘과 자료구조의 최적화도 함께 수행합니다.

- 현재까지도 **2015년도 코드**를 사용 중이며, 단일 스레드 기반이라 **실행 속도가 매우 느림**
- **분석 데이터 규모는 계속 증가**하고 있으나, 기존 구조로는 처리에 한계 존재
- 멀티스레드 리팩토링을 통해 **본래 기능과 탐색 정확도를 유지**하면서도 수행 시간을 **대폭 단축** 가능
- 연구실 내 다양한 과제에서의 **실제 활용도 향상**이 기대됨

### ✅ 프로젝트 수행을 통한 개인 역량 향상

이번 프로젝트는 세 가지 성장을 경험했습니다. 
- 첫째: 복잡한 코드 분석 및 구조 리팩토링 능력 향상. 병렬처리 구조를 직접 설계, 구현하며 동시성문제를 해결하고 최적의 방법을 고민하며 몰입을 통한 성장을 경험했습니다. 
- 둘째: 자료구조/알고리즘을 집요하게 분석해 실험으로 검증하며 수업과 과제에서 배운 이론을 실무에 적용해 보는 경험.
- 셋째: JVM에 대해 공부하고 프로그램의 특성에 맞는 방법들을 떠올리고 적용해 검증하는 경험을 통한 성장.

> 이러한 역량은 향후 **대용량 데이터 병렬처리 시스템**, **시스템 소프트웨어 분야** 진출 시 큰 경쟁력이 될 것입니다.

### ✅ 1. 병렬처리 아키텍처 

**성과**: 5600초 -> 188초. 약 30배 성능 향상.

**아이디어**: Constants.java의 가변 상태(Not read-only) 를 스레드 수(1~36 선택) 길이의 슬롯 배열로 만들고, 각 스레드는 할당받은 자신의 index(0..35) 로만 읽고/쓰기.

**접근 규칙**: Thread i → arr[i] 만 사용(쓰기 충돌 0, 락 0). 공통 룰/테이블/LUT 등 읽기 전용 데이터는 한 번 로딩 후 공유(immutable). 작업 단위(스펙트럼/부분 문제) 처리 → per-slot 버퍼에 중간 결과 축적 → 수집기(Collector) 가 최종 병합.

**메모리 전략**: 시작 시 슬롯 버퍼를 사전 할당(pre-allocation) 하고 매 작업은 reset 만 수행 → GC 부하감소

### ✅ 2. 알고리즘/자료구조 개선

**성과**: 188초->155초. 약 18% 성능향상.

**진행 방법**: 코드분석->개선방안 탐색->코드수정->인텔리제이 Profiler를 활용해 함수 수행시간을 비교.

- StringBuffer 대신에 String을 사용해서 내부 재할당 문제도 해결하고, GC부담도 완화하며 성능 개선
- 필드로컬 캐시와 곱셈연산 감소를 통해 성능을 개선했다.
- 두개의 Peak 리스트를 index 두개로 스캔하는 방식으로 로직 변경. 객체생성과 불필요한 데이터 생성 감소로 성능 개선. 
- Sort 로직을 수행하는 함수에서 자료구조만 LinkedList에서 ArrayList 로 변경. 인덱스 순회 때문에 성능 대폭 개선가능.

### ✅ 3. JVM GC 변경

**성과**: 155초->147초(GC만 변경)->141초(메모리 할당). 약 5~10% 성능향상. 

**아이디어**: 프로그램의 특성상 Young 메모리 영역 그중에서도 Eden영역에 read/write가 집중되는 특성 발견. JVM기본 설정인 G1 GC가 아닌, 프로그램의 특성에 맞는 parallel GC 사용 및 Young-Eden 영역을 더 많이 할당하는 방식으로 분석시간 5~10% 단축 성공

**Parallel GC가 유리한 이유**: Stop-the-world는 길지만 **수집 자체를 다코어로 폭압 처리** → **총 수집시간/총 실행시간 단축**. 배치성 워크로드는 **지연보다 처리량**이 중요.
